## Purpose

定义用户在指定共享账号真实 7 天周期内的动态费用份额与验收行为。本规格对应[需求提案](../../proposal.md)。D01～D03、技术设计和实现计划均已确认，本地实现和分层验收结果见[验收记录](../../verification.md)。正式 Fork 发布与生产验收尚未执行。

## ADDED Requirements

### Requirement: 配额按用户与账号真实周期独立累计

系统 MUST 以 Sub2API 用户、指定上游账号及该账号真实周期为配额边界。同一用户的多把 Key MUST 共用该用户在该账号的周期用量，不同账号的用量 MUST 独立。基础分配场景为参与用户均分，参与人数 MUST 按有效参与用户身份去重，MUST NOT 按在线人数、调用人数或 Key 数量计算。

#### Scenario: 三个用户均分一个共享账号
- **WHEN** 一个账号的最新有效预计总费用为 $1,500，A、B、C 三个有效参与用户均分
- **THEN** 三个用户的当前个人额度 MUST 各为 $500
- **THEN** 各用户在该账号的已用金额 MUST 分别累计

#### Scenario: 同一用户使用多把 Key
- **WHEN** A 的两把 Key 分别在同一账号同一周期实际扣费 $200 和 $150
- **THEN** A 在该账号该周期的已用金额 MUST 为 $350
- **THEN** 新建或切换 Key MUST NOT 重新获得一份额度

#### Scenario: 同一用户使用不同账号
- **WHEN** A 在账号 X 实际扣费 $100，在账号 Y 实际扣费 $40
- **THEN** X 的用户周期已用 MUST 只增加 $100，Y 的用户周期已用 MUST 只增加 $40

#### Scenario: 用户下线或暂时不调用
- **WHEN** 已配置参与分配的用户暂时离线、没有请求或拥有多把 Key
- **THEN** 分配人数 MUST 保持按有效参与用户去重后的数量，不得因这些状态自行变化

### Requirement: 预算复用现有预计总费用而用量累计实际扣费

系统 MUST 复用账号现有 7 天预计总费用的计算语义：本周期账号统计费用乘以 100，再除以上游已用百分比。个人额度 MUST 等于最新有效预计总费用乘以当前个人份额；均分时份额为参与人数的倒数。个人已用金额 MUST 复用现有实际扣费结果，MUST NOT 以模型原价、账号统计费用、Pro 月费或重新计算的售价替代。

#### Scenario: 账号统计费用与实际扣费不同
- **WHEN** 一次请求的账号统计费用为 $20，Sub2API 对用户的实际扣费为 $10
- **THEN** 该用户的周期已用 MUST 增加 $10
- **THEN** 账号预计费用的基数 MUST 继续使用现有账号统计口径，不能因本次新增功能而替换为用户费用

#### Scenario: 用户定价规则影响实际扣费
- **WHEN** 一次请求经过现有模型、倍率或服务层级规则后实际扣费为 $12
- **THEN** 个人周期已用 MUST 增加最终实际扣费的 $12，不得再次套用倍率
- **THEN** 记录本配额用量 MUST NOT 再扣一次用户余额

#### Scenario: 展示舍入不改变判断
- **WHEN** 有效金额包含超出界面显示精度的小数
- **THEN** 配额计算和请求判断 MUST 使用与现有扣费精度一致的金额，不能从已舍入的展示文本反算

### Requirement: 有效预计总费用变化实时影响后续请求

系统确认新有效预计总费用后，后续请求 MUST 使用新预算计算个人额度，MUST NOT 等待账号下一周期、自然周、人工刷新或离线批处理。这里的实时是指已获得有效数据后的生效行为，不代表能够获知尚未采样到的上游变化。

#### Scenario: 预计总费用上升
- **WHEN** 三人均分的预计总费用从 $1,500 变为 $1,800，A 当前已用 $450
- **THEN** A 的额度 MUST 即时变为 $600，账面剩余为 $150
- **THEN** 本周期已用 MUST 仍为 $450

#### Scenario: 预计总费用下降导致超出新额度
- **WHEN** 三人均分的预计总费用从 $1,500 变为 $1,200，A 当前已用 $450
- **THEN** A 的额度 MUST 即时变为 $400，账面剩余显示为 $0
- **THEN** 后续请求 MUST 不再向该账号发起新调用，并按授权回退规则尝试其他账号
- **THEN** 已用 MUST 保留 $450，不能修改为 $400 或产生退款

#### Scenario: 原先耗尽的用户因涨额恢复
- **WHEN** A 已达到该账号个人额度，之后新有效预计值使个人额度高于当前已用
- **THEN** A MUST 能在原周期恢复使用新增的可用额度，无需管理员重置用量

### Requirement: 参与人数与份额配置变化实时生效且不重置用量

管理员成功保存参与用户集合或份额配置后，系统 MUST 对后续请求按新分配关系计算额度，MUST NOT 将变化延迟到下一账号周期。集合与份额变化 MUST 保留本周期已实际扣费的历史。本条不单独增加不等份额编辑功能的首版范围，但任何已提供的份额调整 MUST 遵守相同的实时规则。

#### Scenario: 三人变为四人均分
- **WHEN** 预计总费用为 $1,800，参与人数从三人变为四人，A 当前已用 $450
- **THEN** A 的额度 MUST 从 $600 即时变为 $450
- **THEN** A 已用 MUST 仍为 $450，后续请求应视为该账号个人额度耗尽

#### Scenario: 四人变回三人均分
- **WHEN** 同一周期参与人数从四人恢复为三人，预计总费用仍为 $1,800，A 当前已用 $450
- **THEN** A 的额度 MUST 即时恢复为 $600，账面剩余为 $150

#### Scenario: 移除用户后重新加入
- **WHEN** A 在当前周期已用 $450，被移出分配集合后又在同一周期加入
- **THEN** A 的已用 MUST 仍为 $450，不能因为分配关系重建而从零开始
- **THEN** 其他成员的份额 MUST 随每次已生效的集合变化实时更新

#### Scenario: 新参与用户在该周期已有历史扣费
- **WHEN** A 被加入分配集合前，已经在该账号当前周期实际扣费 $100
- **THEN** A 的周期已用 MUST 承接这 $100，不得只从加入时间开始累计

### Requirement: 额度用尽仅限制对应用户对对应账号的新请求

某用户在某账号本周期的已用达到或超过当前个人额度时，系统 MUST 停止为该用户向该账号发起新请求。该结果 MUST NOT 被实现为账号全局停用，也不能影响其他用户在该账号上的剩余额度。账面剩余 MUST 不小于零；已经开始的请求 MUST 正常完成并据实结算，允许单次结算尾差，同时 MUST 控制并发在途占用。

#### Scenario: 个人额度刚好用尽
- **WHEN** A 的当前个人额度和已用均为 $500
- **THEN** A 的后续请求 MUST 不再向该账号发起新调用

#### Scenario: 一个用户耗尽而其他用户仍有额度
- **WHEN** A 在该账号额度已用尽，B 在该账号仍有可用额度
- **THEN** 系统 MUST 继续允许 B 在满足既有检查时使用该账号
- **THEN** 账号本身 MUST NOT 因 A 的个人耗尽被标记为全局不可调度

### Requirement: 账号真实重置统一恢复个人周期用量

系统 MUST 跟随账号真实 7 天额度重置切换用户周期用量，MUST NOT 按自然周、用户首次调用时刻或 Key 自身周期分别恢复。只有确认账号真实重置才可恢复周期用量；普通采样更新、预计费用变化或同一周期的时间漂移 MUST NOT 被视为重置。

#### Scenario: 周三下午重置的账号
- **WHEN** 账号真实重置时刻为周三 15:00，A、B、C 首次调用时刻不同
- **THEN** 三个用户 MUST 跟随同一次账号重置恢复周期用量
- **THEN** 周一 00:00 或各自首次调用满七天 MUST NOT 单独恢复该账号的个人用量

#### Scenario: 重置时间出现小幅采样漂移
- **WHEN** 同一账号周期的后续采样使预计重置时刻出现秒级偏差，但没有发生真实重置
- **THEN** 系统 MUST 保留原周期累计金额，不能仅因时间戳变化清零

#### Scenario: 新周期还没有有效预计值
- **WHEN** 账号已真实重置，但当前周期预计总费用的输入尚不完整
- **THEN** 系统 MUST 区分“周期已切换”与“新估值可用”两个事实
- **THEN** 有最近有效预计值时系统 MUST 暂用该值，并明确标识暂用状态，等待新周期有效估值更新
- **THEN** 从未有有效预计值时系统 MUST 先完成受控初始化，不能把缺值当作无限额

### Requirement: 缺失或无效估值采用已确认的暂用与初始化规则

系统 MUST 在暂时缺少当前有效预计值时使用最近有效预计值，并记录来源周期、原估值时间和暂用状态；新有效估值到达后 MUST 实时替换。没有任何有效历史值时 MUST 进入待初始化状态，并提供受控初始化路径。暂用有效期、初始化样本与异常处理在技术设计中明确，MUST NOT 自动填入固定的 $1,500，也不能将零、空值、无穷或异常值视为无限预算。

#### Scenario: 新周期暂用最近有效估值
- **WHEN** 上个周期最后有效预计值为 $1,500，新周期已真实重置且尚无新有效预计值，三个用户均分
- **THEN** 在规定的暂用有效期内，个人额度 MUST 暂按 $500 计算，新周期已用从真实重置后的费用开始累计
- **THEN** 管理侧 MUST 能识别该预算来自历史暂用值

#### Scenario: 第一个有效估值到达
- **WHEN** 暂用预算期间获得本周期 $1,200 的有效预计值，三个用户均分
- **THEN** 个人额度 MUST 即时变为 $400，已发生的本周期实际扣费 MUST 保留

#### Scenario: 从未产生有效预计值
- **WHEN** 一个账号没有可用的当前估值或历史有效估值
- **THEN** 系统 MUST 明确显示待初始化，并提供有边界的初始化流程
- **THEN** 普通请求 MUST NOT 获得未定义的无限额度，初始化 MUST NOT 形成无限自动探测循环

#### Scenario: 后续采样返回无效值
- **WHEN** 当前没有收到有效新估值，只出现零利用率、缺失字段或非法金额
- **THEN** 系统 MUST 保留最近有效值及其真实时间，不得用异常样本伪造新鲜的有效预算

### Requirement: 个人耗尽后尝试其他授权账号并准确说明失败原因

系统 MUST 在某账号个人额度耗尽后继续尝试用户明确有权使用、能力匹配且仍可用的其他账号，MUST NOT 选择无权账号。无其他可用额度时 MUST 返回可辨识的账号额度已用尽提示。跨分组时 MUST 仅选择明确授权的回退分组，并按最终执行分组计费；MUST NOT 将其他 Key 的存在直接等同于当前请求的跨组权限。

#### Scenario: 存在其他授权可用账号
- **WHEN** A 对账号 X 的个人额度已用尽，账号 Y 在确认的回退范围内、有使用权限、支持所请求模型且仍可用
- **THEN** 请求 MUST 尝试 Y
- **THEN** 在 Y 上成功执行后的实际扣费 MUST 计入 A 在 Y 的周期用量，不得继续计入 X

#### Scenario: 没有其他可用额度
- **WHEN** 用户授权候选中所有账号的个人额度均已耗尽
- **THEN** 系统 MUST 提示账号额度已用尽，不能无限重复选择已耗尽账号
- **THEN** 在已知恢复时间时 MUST 提供可理解的恢复时间信息，不得编造未知时间

#### Scenario: 其他账号不在授权范围
- **WHEN** 系统中存在有额度的账号，但用户或当前请求未被授权使用
- **THEN** 系统 MUST NOT 为绕过个人额度限制而使用该账号

#### Scenario: 候选因其他原因不可用
- **WHEN** 候选还存在上游限流、模型不匹配、账号停用或其他既有不可用原因
- **THEN** 系统 MUST 保留可定位的原因区分，不能一律误报为个人额度已用尽

#### Scenario: 自动切换到授权回退分组
- **WHEN** 原分组的可用账号个人额度已耗尽，明确授权的回退分组中存在可用账号，且用户及本次请求满足目标分组约束
- **THEN** 系统 MUST 自动尝试该回退分组，不要求客户端另行换 Key
- **THEN** 实际扣费和订阅用量 MUST 按最终执行分组的有效规则计算，仍归属原请求的用户与 Key

#### Scenario: 回退权限已撤销
- **WHEN** 原先允许的回退分组已不再授权，或用户不满足该分组现有访问或订阅条件
- **THEN** 后续请求 MUST 不再进入该分组，不能继续使用旧授权快照绕过限制

#### Scenario: 会话状态无法跨账号迁移
- **WHEN** 请求需要原账号持有的上游会话状态，原账号个人额度耗尽且状态无法完整重建
- **THEN** 系统 MUST 明确提示额度或会话迁移限制，不能静默切换后丢失上下文，也不能继续消耗原账号额度

### Requirement: 多入口和重复结算不能绕过或重复累计配额

系统 MUST 对所有能使用受控账号的既有计费入口保持相同的配额语义，MUST NOT 因接口别名、流式请求、粘性会话或长连接后续轮次而绕过限制。重复处理同一笔已经应用的扣费 MUST NOT 再次增加个人已用。系统 MUST 在准入时计入并发在途占用，并将请求固定到发起时确认的账号周期；响应结束或异步扣费发生在新周期时 MUST NOT 错记新周期。

#### Scenario: 使用另一兼容入口调用同一账号
- **WHEN** 同一用户通过不同既有兼容入口调用同一受控账号
- **THEN** 个人已用 MUST 合并累计，额度耗尽判定 MUST 保持一致

#### Scenario: 已建立连接中的后续请求
- **WHEN** 首轮请求后个人额度已耗尽，用户在同一长连接中发起新一轮模型执行
- **THEN** 新一轮 MUST 重新遵守当前有效额度，不能复用连接建立时的放行结果

#### Scenario: 同一扣费重复处理
- **WHEN** 同一笔实际扣费因重试被重复送达累计路径
- **THEN** 个人周期已用 MUST 只增加一次

#### Scenario: 并发请求不能共同忽略已有占用
- **WHEN** 一个用户账面剩余 $10，某个在途请求已占用 $8，又有需要占用 $8 的新请求
- **THEN** 新请求 MUST 不得仅因账面已用尚未结算而直接在同一账号放行
- **THEN** 系统 MUST 尝试其他授权可用账号，或返回可定位的额度占用结果

#### Scenario: 实时降额时已有请求正常结束
- **WHEN** 请求已经开始执行，此时预计费用下调导致个人额度低于已用和在途占用
- **THEN** 系统 MUST 允许该请求正常结束并按实际费用累计，后续请求 MUST 按新额度判断
- **THEN** 系统 MUST NOT 修改实际账单以伪装未超限，也不能因为允许尾差而继续无限放行新请求

#### Scenario: 跨账号周期结算
- **WHEN** 一个请求在账号周期 P 发起并占用额度，在周期 P+1 才完成扣费
- **THEN** 该次账号个人用量 MUST 归入 P，P+1 的用量 MUST NOT 被误加
- **THEN** 该次用户实际扣费 MUST 仍按既有规则正常结算一次

### Requirement: 管理侧能够核验动态额度及生效状态

系统 MUST 让有权管理员配置参与分配的用户，并能够核验账号最新有效预计费用及更新时间、当前参与人数或份额、账号周期及重置时间、各用户个人额度、实际已用和账面剩余。已有无效或过期估值时 MUST 明确显示状态，MUST NOT 伪装为新鲜的有效预算。具体页面和接口由技术设计确定。

#### Scenario: 查看三人均分后的配额
- **WHEN** 管理员查看一个已配置动态额度的账号
- **THEN** 管理侧 MUST 能核对每个参与用户的份额、额度、已用和剩余，以及这些数值对应的周期和估值时间

#### Scenario: 没有刷新页面仍需执行新额度
- **WHEN** 用户或管理员没有刷新浏览器，但服务端已获得新有效估值或保存新分配配置
- **THEN** 后续请求 MUST 仍按新额度执行，不能把页面刷新作为生效条件

### Requirement: 配置变更与受支持升级保留周期用量

系统 MUST 在普通进程重启和受支持升级路径中保留本功能配置、账号当前周期和个人已用金额，且运行时限制继续执行。管理员调整配置、移除再加入或停用后重新启用配额 MUST NOT 擦除同一周期的历史扣费。技术设计 MUST 说明受支持的升级及回滚路径，不能声称任意官方原版覆盖都能保留定制功能。

#### Scenario: 周期中途升级
- **WHEN** 升级前 A 在该账号当前周期已经实际扣费 $450，升级过程中没有额外调用或真实重置
- **THEN** 升级后 A 的已用 MUST 仍为 $450
- **THEN** 额度 MUST 继续按最新有效估值计算，运行时限制 MUST 生效

#### Scenario: 重启或重新启用本功能
- **WHEN** 同一账号周期内进程重启，或管理员停用后重新启用配额
- **THEN** 系统 MUST 继续承接该周期的实际扣费，不能重新授予完整预算

#### Scenario: 在周期中途首次启用
- **WHEN** A 已在该账号当前周期实际扣费 $100，此时首次启用动态配额
- **THEN** 系统 MUST 将有可靠依据的 $100 承接为本周期已用
- **THEN** 历史依据不足时 MUST 暴露待核对状态，不能伪装为已完整初始化

### Requirement: 新增配额保持既有计费与权限约束

新增账号个人配额 MUST 与原有鉴权、模型权限、用户余额、Key 限额、平台限额、订阅额度及账号上游可用性共同生效，MUST NOT 通过拥有个人份额自动绕过任何既有限制。未启用本功能的账号 MUST 保持既有行为。

#### Scenario: 个人账号额度足够但现有限额不满足
- **WHEN** 用户对该账号仍有个人额度，但用户余额或其他现有约束不满足
- **THEN** 系统 MUST 继续按现有约束拒绝或处理请求，不得仅因有份额就放行

#### Scenario: 未启用动态配额的账号
- **WHEN** 账号没有启用本功能
- **THEN** 该账号 MUST 保持既有计费和调度行为，不得被本功能隐式新增限额
