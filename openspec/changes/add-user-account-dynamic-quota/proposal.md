# 用户对共享账号的动态周期额度

## 文档状态

- 阶段：需求、技术设计及实现计划已确认，已完成本地实现与分层验证；当前维护分支的提交和推送已获用户授权，执行结果以 Git 记录为准，尚未发布或部署。
- 已确定的业务方向：实际扣费累计、复用现有预计总费用、按份额实时分配、跟随账号周期重置、耗尽后使用其他授权账号、升级后保留功能和用量。
- D01～D03 已于 2026-10-18 按推荐选项确认，具体规则见“已确认边界决策”。
- 阅读顺序：本提案 → [验收规格](specs/user-account-dynamic-quota/spec.md) → [技术设计](design.md) → [实现计划](tasks.md)与[验收矩阵](verification.md)；实际实现和证据以验收记录为准。

## Why

多个用户共享一个上游订阅账号时，需要限制每个人在该账号一个真实额度周期内可消耗的金额，避免一个用户提前消耗其他人的份额。

例如，某 GPT Pro 账号当前 7 天预计总费用为 $1,500，三个用户均分时每人额度为 $500。预计总费用会随使用变化，个人额度也必须同步变化，不能固定填写 $500，也不能把变化推迟到下一周期。

现有用户平台限额、API Key 限额和订阅限额的累计对象或周期与本需求不同，无法直接组合得到“用户 × 指定账号 × 账号真实周期”的动态额度。

## What Changes

- 为指定共享账号提供按用户分配周期费用额度的能力，以三人均分为基础验收场景。
- 复用现有账号 7 天“预计总费用”作为预算基数，按 Sub2API 对用户的实际扣费累计个人已用金额。
- 预计总费用、参与用户集合或已生效份额配置发生变化时，对后续请求实时重算额度。
- 额度变化只改变可用上限；本周期已经发生的扣费持续保留。
- 所有参与用户跟随账号同一次真实 7 天额度重置恢复周期用量，不按自然周或用户各自的首次使用时间重置。
- 个人对某账号的额度耗尽后，继续尝试其他有权使用的账号；不存在其他可用额度时明确提示。
- 升级后保留配置、当前周期及已用金额，防止功能丢失、额度误清零或重复授予预算。

## Capabilities

### New Capabilities

- `user-account-dynamic-quota`：定义用户在共享账号真实周期内的动态费用份额、实际扣费累计、实时调整、耗尽后的授权回退，以及升级连续性。

### Modified Capabilities

无。本变更不修改现有模型售价、用户余额、平台限额或订阅额度的业务含义。

## Impact

- **管理员**：需要配置参与分配的用户，并核验账号预计费用、个人额度、已用金额、剩余额度和重置时间。
- **用户请求**：同一用户使用不同 Key 或不同兼容入口访问同一账号时，必须合并累计；耗尽后可能发生授权范围内的账号切换。
- **既有业务**：账号状态、上游限流、模型权限、鉴权和已有额度检查继续生效。
- **升级交付**：维护版本明确支持的升级路径、数据保留、兼容验证和回滚限制，不能仅承诺保留配置文件。
- **实现范围**：预计涉及账号用量、估值、份额配置、调度、计费和管理侧展示；具体模块边界、接口和数据结构见技术设计。

## 业务定义与计算口径

| 名称 | 定义 |
| --- | --- |
| 用户 | Sub2API 用户身份，同一用户的多把 Key 不形成多个配额主体 |
| 账号 | 被配置和限制的 Sub2API 上游账号，首个验收对象为 OpenAI OAuth 账号的 7 天额度 |
| 账号周期 | 该账号上游真实额度窗口，不是自然周，也不是用户首次调用后自行开始的 7 天 |
| 预计总费用 `E` | 现有页面展示的本周期满额预计费用，属于估算预算，不是 Pro 月费、真实现金余额或预计剩余费用 |
| 参与用户 | 被纳入该账号份额分配的有效用户，以用户身份去重；人数不按在线人数、调用人数或 Key 数量计算 |
| 个人份额 `s` | 该用户在当前分配中的占比；三人均分时均为 `1/3`，不等份额编辑能力不默认扩入本期范围 |
| 个人额度 `Q` | 最新有效预计总费用乘以当前个人份额 |
| 个人已用 `U` | 本周期该用户在该账号上已经实际扣费的累计金额 |
| 账面剩余额度 `R` | 个人额度扣除已用金额后的非负余额；在途占用和执行中请求的处理取决于 D02 |

```text
个人额度 Q = 最新有效预计总费用 E × 当前个人份额 s
均分时 s = 1 / 当前参与人数 N
个人已用 U = 当前账号周期内该用户在该账号上的实际扣费之和
账面剩余额度 R = max(Q - U, 0)
```

当前已有预计费用的计算语义为：

```text
E = 本周期账号统计费用 × 100 / 上游本周期已用百分比
```

这里的“账号统计费用”与用户实际扣费是不同口径。本需求沿用前者计算预算基数，用后者累计个人用量，不替换或混同两个金额字段。计算使用未作展示舍入的有效金额，界面显示精度不能改变扣费或准入结果。

## 已确认规则

| 编号 | 规则 |
| --- | --- |
| C01 | 计量维度为用户、指定账号和该账号的真实周期；不同账号分别累计 |
| C02 | 个人已用金额按照 Sub2API 对该用户的实际扣费累计，复用既有计费结果 |
| C03 | 预算基数复用现有预计总费用，不额外增加固定的 $1,500 账号总额上限 |
| C04 | 预计费用、参与人数和已生效份额配置变化均实时影响后续请求，不等待下一周期 |
| C05 | 降额后已用达到或超过新额度时停止向该账号发起新请求；涨额后重新出现可用额度时恢复使用 |
| C06 | 调整配置、移除后重新加入、更换 Key 或刷新页面均不清空本周期已用金额 |
| C07 | 账号真实重置时，参与用户的周期用量统一恢复；同一周期的采样时间漂移不构成重置 |
| C08 | 某用户耗尽不会停用整个共享账号，其他用户仍可使用自己的剩余额度 |
| C09 | 有其他授权且可用的账号时继续尝试；没有其他可用额度时提示账号额度已用尽 |
| C10 | 功能及配置、当前周期和已用金额在受支持的升级路径中保持连续，不误清零或重复发放额度 |

“实时”指系统确认新有效估值或成功保存配置后，后续请求无需等待自然周、账号下一周期、人工刷新或离线批处理即可使用新额度。系统尚未收到的上游变化不视为已经获知；采样新鲜度和一致性实现由技术设计说明。

参与集合和份额变更只调整分配关系，不自动扩大账号访问权限。把额度分给用户不能代替原有鉴权；也不能通过重新创建配额关系获得一份新的周期预算。

## 实时变化示例

以下每行是同一账号周期内连续发生的变化，用户 A 已实际使用 $450；期间没有新增扣费，所有参与用户均分。

| 变化 | 最新预计费用 | 人数 | A 的额度 | A 的已用 | A 的账面剩余及后续请求行为 |
| --- | --- | --- | --- | --- | --- |
| 初始状态 | $1,500 | 3 | $500 | $450 | 剩余 $50 |
| 预计费用下降 | $1,200 | 3 | $400 | $450 | 剩余 $0，对该账号停止新请求并尝试其他授权账号 |
| 预计费用上升 | $1,800 | 3 | $600 | $450 | 恢复使用，剩余 $150 |
| 新增一个参与用户 | $1,800 | 4 | $450 | $450 | 额度即时降低，剩余 $0 |
| 参与人数恢复为三个 | $1,800 | 3 | $600 | $450 | 额度即时恢复，剩余 $150 |

如果 A 被移除后在同一周期重新加入，其已用仍为 $450。新成员加入前在该账号同一周期已经发生的扣费也不能因新建分配关系而遗漏。

## 已确认边界决策

以下采用已确认的推荐选项。初始化流程、并发占用和授权校验等实现细节在技术设计中说明，不再将业务选项保留为待定。

| 编号 | 问题 | 已确认决策 | 设计约束 |
| --- | --- | --- | --- |
| D01 | 没有有效预计费用如何处理？ | 短暂沿用最近有效预计值；从无历史有效值时先完成初始化 | 明确暂用状态和有效性；提供受控初始化路径，避免“无估值禁止请求、无请求又无法建立估值”的闭环 |
| D02 | 请求执行中额度耗尽或下调如何处理？ | 已开始的请求正常结束、据实计费；后续请求按最新额度判断，控制并发占用，允许单次结算尾差 | 不承诺金额绝对不超限；不能用允许尾差作为无限并发放行的理由；跨周期在途请求归属必须固定 |
| D03 | 其他有权限账号位于不同分组时如何处理？ | 自动切换到明确授权的回退分组，并按最终执行分组计费 | 不因持有其他 Key 自动扩大当前请求权限；目标分组需重新校验权限、计费资格和模型能力；不可迁移会话明确报错 |

## 页面升级方式

后续定制版本的设计目标是保留现有“页面检查更新 → 安装更新 → 页面重启生效”的操作方式。更新来源应为包含定制功能且已经验证的 Fork 发布包，不能继续下载未包含该功能的官方原版。

原作者发布新版本后，先把上游更新合入维护版本，验证后在 Fork 发布；页面随后提示可用更新。这不是页面按钮在服务器上执行 Git 合并，也不是 Fork 自动继承官方发布包。

首次从官方程序切换到定制版本需要一次受控部署；安装具备新更新源逻辑的定制版本后，才支持后续页面升级。检查更新、下载、版本比较、缓存、回滚及手动恢复指引需统一，细节见技术设计。更新逻辑已在本地实现并完成模拟升级/回退；Fork 正式制品尚未发布，详见[维护指南](../../../docs/maintenance/user-account-quota.md)。

## 范围与兼容要求

- 本期以共享 OpenAI OAuth 账号的 7 天周期为验收对象；其他平台、5 小时额度分配和不等份额编辑能力不自动包含在已确认范围内。
- 不改变模型定价、倍率、用户余额扣款方式或现有平台、Key、订阅限额的含义，也不因为新增配额再扣一次用户余额。
- 本需求不要求根据其他用户的空闲情况自动借用其未用份额，也不引入周期剩余额度结转。
- 未启用本功能的账号保持既有行为；启用范围、未参与用户的处置和管理侧操作方式必须在技术设计中明确，避免形成绕过。
- 有效预计值变化与不可用估值必须区分，不能直接把空值、无穷值或异常值当作可执行的新预算；具体处理受 D01 约束。
- 首次在周期中途启用时，应承接该周期已经发生的扣费，不能从启用时间另送一份额度；历史依据不足时应明确暴露待核对状态。
- “升级后可用”包括运行时限制继续执行、配置保留、用量保留及升级期间在途结算的连续性；仅保留表或文件但停止执行限制不算满足。
- 不承诺用尚未包含本功能的官方原版程序直接覆盖升级仍能保留功能。受支持的升级、回滚和上游同步路径由技术设计具体说明。
