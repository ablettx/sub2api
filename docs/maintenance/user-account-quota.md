# 共享账号的用户动态额度与维护升级

本指南适用于 `ablettx/sub2api` 维护版本。功能范围为 OpenAI OAuth 账号的真实 7 天额度周期，运行模式必须为标准计费模式。需求和技术细节见 [OpenSpec 变更](../../openspec/changes/add-user-account-dynamic-quota/proposal.md)，本地验证结果见 [验收记录](../../openspec/changes/add-user-account-dynamic-quota/verification.md)。

## 配额怎样计算

```text
预计总费用 E = 本周期账号统计费用 × 100 / 上游本周期已用百分比
个人额度 Q = E / 当前配置的参与人数（保留 8 位金额精度并向下截断）
已用 U = 同一用户、同一账号、同一真实周期的实际扣费之和
可用金额 = max(Q - U - 在途占用, 0)
```

账号统计费用用于估算预算，实际扣费用于累计个人已用，二者不能互换。同一用户的所有 Key 合并累计，不同账号分别计算。人数来自管理员配置的成员集合；用户下线、暂时不调用或停用登录不会自动把份额转给其他人。

例如 E 为 $1,500、三人均分时，每人 Q 为 $500。A 已用 $450，E 降到 $1,200 后，A 的 Q 立即变为 $400、可用为零，U 仍为 $450。E 上升或人数减少后，出现可用金额就恢复准入。这里的实时生效指后端收到有效新观测或配置保存成功后的后续请求；上游采样没有到达时不会凭空推测变化。

周期跟随账号真实重置时间，不使用自然周。已发出的请求按开始时的周期据实结算，即使完成时已经跨周期、实时降额或成员已移除。预留用于控制并发，仍允许单次最终结算尾差。

## 管理员配置

1. 在“账号管理”编辑目标 OpenAI OAuth 账号，找到“用户动态额度”区域。保存账号基础资料和保存配额是独立操作。
2. 选择参与用户并开启功能，配置有序的回退分组；没有回退需要时留空。默认估值暂用时间为 30 分钟，可配置为 10 分钟至 24 小时。
3. 保存后核对成员、真实周期、每人额度、已用、在途占用、可用金额及估值时间。页面每 30 秒刷新运行状态，未保存的编辑不会被轮询覆盖；实际准入直接读取最新数据库状态。
4. 首次启用或出现待初始化状态时，先核对该账号当前周期完整账单，再填写核对说明并执行初始化。操作会承接已有消费，不能用重新启用、移除后重加或更换 Key 领取新的额度。

成员资格不授予账号访问权限。受控账号仅允许配置中的成员使用，原有用户、Key、IP、模型、分组、订阅及余额限制继续有效。移除成员保留其历史账本，重新加入承接本周期用量。停用配额期间发生的实际扣费也会承接，重新启用不清零。

配置保存带版本检查。发生冲突时重新读取并确认最新配置后再保存，不能覆盖另一位管理员已经保存的成员或回退顺序。

同一个物理 OpenAI 账号应只保留一个配额所有者。重复别名账号、影子账号、PAT 或 agent 身份不能用来绕过额度；已建配额的账号也不能直接更换物理账号身份。

## 估值缺失、初始化与未决票据

| 状态 | 含义与操作 |
| --- | --- |
| `current` | 当前真实周期有有效估值，后续请求使用该值 |
| `carryover` | 暂用最近有效估值；查看来源时间与暂用截止，读取不会延长期限 |
| `initializing` | 账单或估值尚未准备好，普通请求不向该账号无限放行 |
| `unavailable` | 暂用已到期或数据不可用，等待有效观测、核对或使用其他授权账号 |

初始化优先使用与真实扣费同事务保存的收据，包括归档收据；旧版历史日志作为兼容补充。日志缺失不代表没有消费，缺少可信执行周期的收据不能被自动当成本期零消费。需要核对并补齐依据时应走维护流程，不直接改表清空用量。

默认不发起付费校准。确需校准时，必须在管理页面明确勾选授权，指定计费用户、该用户的 Key 与分组、正数费用预算、1～3 次调用及每次 1～256 个输出 Token。校准走正常扣费链路；无有效利用率、费用边界耗尽或调用失败会停止，不自动扩大预算。最终真实费用可能有单次尾差，不能把预估预算当作严格现金上限。

已发送但消费结果不明的请求保留为 `uncertain`，租期到期或服务重启不会自动释放。管理员核对上游和本地扣费依据后，可从未决票据区域填写说明进行“未发生扣费”的核对释放。后续若收到可信的迟到扣费，系统仍会据实入账；该操作不是退款或清零。

## 额度耗尽与兼容入口

系统先尝试当前分组的其他合格账号，再尝试策略中显式配置的回退分组，且重新核验用户的实际授权和订阅。跨组按最终执行分组的定价和订阅扣费，保留原 Key 身份与限制，不修改数据库中的 Key 分组绑定。

没有其他可用额度时返回 `ACCOUNT_USER_QUOTA_EXHAUSTED`，有在途占用但金额不足时返回 `ACCOUNT_USER_QUOTA_INFLIGHT`，通常为 HTTP 429。估值、初始化或依赖不可用为 503；无法完整迁移的会话为 409。WebSocket 使用对应错误帧，每个 `response.create` 重新检查。

Responses、Chat Completions、Messages、同步和异步单图、独立 Alpha Search 共用准入和结算。异步单图在后台实际执行时重新鉴权。Live 当前没有真实费用结算链，首版调度排除受控账号并尝试其他合格账号；无候选时明确提示未接入计量。启用配额前应核对已有 Live 会话并结束或等其自然完成。Embeddings 继续仅支持其原有 API Key 账号能力。

## 以后如何更新

安装维护版之后，非 Docker 的日常操作仍为：

```text
页面检查更新 → 确认来源为 ablettx/sub2api · stable → 安装更新 → 立即重启
```

页面显示的更新来自 Fork 已验证的发布版本。原作者发布新版本后，维护者先把上游代码合入维护分支，解决冲突并完成回归，再发布新的 Fork 维护版本；页面才会提示更新。页面更新按钮不执行 Git 合并。

版本格式为 `上游版本-ablett.维护修订`，例如 `0.2.17-ablett.1`、`0.2.17-ablett.2`。相同上游基线的修订也能被发现。默认稳定渠道排除预发布和仅含镜像的发布，不会下载不含本功能的官方原版包。

首次从官方程序切换需要一次受控部署，原版页面不能自动切换到 Fork 来源。首次部署前准备数据库备份和程序副本，核对环境、成员、真实周期、历史消费与 Live 会话；部署后确认维护版本来源并完成真实业务验收。Docker 部署通过维护镜像更新容器，不支持页面内替换容器中的二进制。

重启时暂停受控请求的新准入，等待活跃占用和扣费队列排空，最多 30 秒。仍在结算或数据库无法确认时取消重启、恢复准入并返回可重试原因；已知未知票据继续保留。安装后尚未重启时，页面要求先重启，避免重复覆盖程序和备份。

## 维护者合并与发布

最近的上游同步及迁移衔接见 [v0.2.18 同步记录](upstream-v0.2.18.md)。

1. 从上次已验证的维护版本创建维护分支，获取 `upstream`（`Wei-Shaw/sub2api`）最新代码，在维护分支解决合并冲突。不要用原版二进制覆盖维护程序。
2. 重点检查调度、各执行入口、身份与定价、统一扣费事务、迁移和更新器。后续迁移使用独立文件名；已经应用的 `246_ablett_account_user_quota.sql` 及其他迁移不得改写 checksum。
3. 执行 [验收记录中的检查](../../openspec/changes/add-user-account-dynamic-quota/verification.md)，确认金额、票据、版本发现及嵌入前端连续。提交、推送、标签和发布按实际操作分别取得授权。
4. 使用现有 release workflow 构建同一提交的前后端。二进制更新需要完整的目标平台归档、`checksums.txt` 及 `manifest-<os>-<arch>.json`，正式发布必须使用干净的目标标签提交；本地模拟夹具不作为正式制品发布。
5. manifest 记录 Fork 来源、渠道、上游版本、修订、提交、平台、归档和二进制 SHA-256、配额能力、数据库兼容范围、回滚下界及迁移清单。发布后实查稳定标志、`releases/latest`、目标架构资产和下载可用性，再进行受控上线。

## 回退边界

页面指定版本回退和本地备份恢复都必须通过兼容校验：包含动态配额能力、能读取当前数据库和票据、满足回滚下界、迁移 checksum 一致。官方原版 `.backup` 或无兼容元数据的备份会被拒绝。

数据库迁移采用向前兼容方式，不随程序回退自动撤销。更新器对当前数据库已有迁移采用严格校验；目标版本缺少某个已应用迁移、checksum 不同或超出兼容范围时拒绝更新/回退。历史迁移 checksum 白名单也可能需要维护者专门核验，不能通过跳过校验恢复。

确需回退到不支持当前结构的程序时，需要单独制定数据库与程序共同恢复方案，在明确授权后执行。不要删除账本、占用或迁移记录来强行通过兼容检查。
